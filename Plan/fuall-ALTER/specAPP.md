# ALTER — Спецификация приложения (specAPP.md)

> Мобильное приложение поверх той же платформы, что и сайт (specWEB.md).
> Не отдельный продукт с нуля — тот же бэкенд/данные, тот же Profile Hub / Maker Studio / Credit & Consent,
> но с мобильными сценариями, которых на вебе нет или которые там неудобны.
> Порядок реализации: **сайт → приложение** (сайт уже сделан).

---

## 1. Роль приложения относительно сайта

Сайт (Next.js на Vercel) остаётся источником истины и точкой входа для не-зарегистрированных пользователей — публичные страницы `/u/[username]` и `/u/[username]/commission` должны индексироваться и открываться без установки приложения (иначе теряется вирусность через шеринг ссылок).

Приложение — не «обёртка сайта», а слой для того, что мобильный контекст делает лучше:

- **Быстрая публикация** — фото прямо с камеры/из галереи в билд или историю, без загрузки файлов через браузер
- **Push-уведомления** — новая заявка на коммишен, подтверждён депозит, приближается дедлайн, кто-то запросил согласие на фото
- **Maker Studio на ходу** — мейкер отвечает клиенту, двигает карточку заказа, отмечает оплату депозита не за компьютером
- **Офлайн-просмотр** — свои билды/истории и открытые заказы кэшируются, доступны без сети (на конвентах интернет часто плохой)
- **Deep links** — пуш или ссылка из Telegram открывает конкретный экран приложения (карточку заказа, профиль), а не просто общий стартовый экран

Всё остальное (Explore, чтение чужих профилей, форма запроса коммишена без регистрации) может открываться и в системном браузере/webview — не дублируем то, что сайт уже делает быстро.

## 2. Технический стек

| Слой | Технология | Причина |
|---|---|---|
| Framework | **React Native + Expo** (managed workflow) | один код на iOS/Android, быстрый старт, EAS Build/Submit без своей CI-инфраструктуры |
| Навигация | Expo Router (file-based, тот же ментальный паттерн, что Next.js App Router на сайте) | согласованность с вебом, легче держать одну команду |
| Бэкенд/данные | **тот же Turso + тот же API-слой**, что у сайта (общие эндпоинты, не отдельный бэкенд) | одна модель данных, не расходится с вебом |
| ORM/типы | Drizzle-сгенерированные типы переиспользуются из веб-репозитория (монорепо) | не дублировать схему вручную |
| Аутентификация | Тот же Auth.js/OAuth-провайдер, сессия через secure token (Expo SecureStore) | единый аккаунт веб+приложение |
| Push | Expo Push Notifications → на бэкенде та же таблица `notifications`, что и на вебе | не два разных пайплайна уведомлений |
| Медиа | Загрузка через тот же Vercel Blob/R2-эндпоинт, с компрессией на устройстве перед отправкой | быстрая загрузка на мобильном интернете/на конвенте |
| Офлайн-кэш | React Query + persistent cache (MMKV) для «своих» данных: профиль, билды, заказы | мгновенное открытие приложения, работа без сети |
| Стили | Дизайн-система ALTER, токены переносятся 1:1 из specWEBDizain.md (см. §4) | единая айдентика веб+приложение |
| Аналитика/крэши | Expo/Sentry | стабильность на старте важнее кастомной аналитики |

**Требования к производительности:**
- Холодный старт до интерактивного экрана — не более ~2с на среднем Android-устройстве
- Изображения — превью грузятся первыми (blur-placeholder → полное качество), не блокируют скролл ленты
- Списки (билды, заказы, Explore) — виртуализация (FlashList), не рендерим весь массив разом
- Загрузка фото — в фоне, с индикатором прогресса, не блокирует остальной интерфейс приложения
- Push обрабатывается даже при закрытом приложении (background handler) — статус заказа обновляется без открытия

## 3. Функциональные модули (приложение)

### 3.1 Онбординг
- Выбор роли(-ей): косплеер / мейкер / фотограф (можно несколько, как на вебе)
- Вход/регистрация — тот же аккаунт, что и на сайте (email + Google/Apple OAuth; на iOS Apple OAuth обязателен политикой App Store, если есть другой OAuth)
- Быстрая настройка профиля: аватар, никнейм — с возможностью пропустить и заполнить позже

### 3.2 Лента / Explore
- Курируемые подборки, как на вебе (не бесконечный алгоритмический скролл) — «Новые билды», «Открытые коммишены», «По франшизе»
- Фильтры-чипы (роль, статус коммишена, франшиза, страна)
- Поиск

### 3.3 Профиль (свой и чужой)
- Просмотр — паритет с `/u/[username]` на вебе: статус коммишена, билды, истории, ссылки, конвенты
- Редактирование своего профиля — с мобильных полей (без перегруженных форм веба)
- Кнопка «Запросить коммишен» — открывает мобильную wizard-форму (см. 3.5) или, если проще, деталь коммишена как модальный флоу

### 3.4 Создание билда / истории
- Билд: фото (камера/галерея, можно несколько), персонаж/франшиза, теги соавторов (мейкер/фотограф) — с автоподсказкой по никнейму
- История: быстрый пост — фото/видео + короткий текст, привязка к билду опционально
- Обязательный шаг согласия при теге фотографа/мейкера — публикация фото ждёт подтверждения второй стороны (пуш ей приходит сразу)

### 3.5 Запрос коммишена (со стороны заказчика)
- Мобильный wizard, тот же порядок шагов, что на вебе: тип работы → референсы (фото из галереи/камеры) → замеры по шаблону → срок и бюджет → подтверждение условий
- Экран подтверждения после отправки, статус заявки виден в разделе «Мои заявки»

### 3.6 Maker Studio (мобильная версия)
- Kanban как свайпаемые колонки-табы (не горизонтальный скролл всех колонок разом — так и на вебе в мобильной адаптации)
- Карточка заказа: клиент, референс-миниатюра, дедлайн, статус депозита — тап открывает деталь
- Деталь заказа: чек-лист этапов (с чекбоксами, тап = отметить выполненным), заметки, кнопка «Отметить депозит оплаченным», шаблон договора (просмотр)
- Быстрые действия свайпом по карточке (например, свайп вправо = следующий статус) — мобильно-специфичный UX, которого нет на вебе
- Календарь загруженности — отдельная вкладка

### 3.7 Уведомления
- Отдельный таб/центр уведомлений: новая заявка, подтверждён депозит, дедлайн приближается (за 3 дня и за 1 день), запрос на подтверждение фото, новый комментарий
- Push дублирует критичные (заявка, дедлайн, запрос согласия) — остальное можно смотреть только в приложении

### 3.8 Credit & Consent
- Тот же механизм, что на вебе: пуш «вас отметили как мейкера/фотографа — подтвердить?», простой экран подтверждения/отклонения
- Публичная цепочка авторства видна на фото в приложении так же, как на сайте

## 5. Модель данных

Отдельной схемы для приложения нет — используется та же схема, что в specWEB.md §4 (`users`, `profiles`, `builds`, `build_photos`, `stories`, `commissions`, `commission_requests`, `orders`, `credits`, `notifications`, `subscriptions`). Добавляется только то, что специфично для мобильного клиента:

```
device_tokens    (id, user_id, expo_push_token, platform, created_at)
offline_cache_meta (не серверная таблица — локальная, для инвалидации кэша на устройстве)
```

## 6. Монетизация (мобильная специфика)

Общая модель — та же, что на вебе (§5 specWEB.md): бесплатный Profile Hub, платный расширенный Maker Studio, выключено на старте.

Мобильная особенность, которую нужно учитывать заранее в архитектуре:
- Если подписка продаётся **через приложение** — Apple/Google берут комиссию (до 30%, ~15% для мелких разработчиков по программам Small Business) и требуют In-App Purchase, внешние платёжные ссылки на оплату подписки в самом приложении показывать нельзя
- Практичный вариант: оплата подписки мейкера оформляется **через сайт** (веб-чекаут), приложение только показывает статус подписки — так не нужно сразу встраивать IAP. Встраивание IAP — отдельная будущая задача, если понадобится покупать что-то именно внутри приложения (например, буст видимости профиля)
- Это решение фиксируется сейчас, чтобы не переделывать флоу оплаты после того, как подписки включат

## 7. Адаптивность / устройства

- iOS 15+ / Android 8+ (баланс охвата и разумной поддержки старых API)
- Экраны от маленьких (iPhone SE, ~375pt) до планшетов — приложение не оптимизируется под планшет отдельно в MVP, но не должно ломаться (адаптивный, не фиксированный лейаут)
- Тёмная тема — единственная тема на старте (дизайн-система и так тёмная по умолчанию), системная светлая тема не поддерживается в MVP
- Поддержка жестов возврата/навигации нативной для каждой платформы (Android back-жест, iOS swipe-back)

## 8. Риски и как их обходим

| Риск | Как обходим |
|---|---|
| Расхождение данных/логики между вебом и приложением | Общий бэкенд/API и общая схема Turso — приложение не заводит свою копию логики |
| App Store/Google Play отклонят из-за оплаты в приложении | Подписка оформляется через веб-чекаут, в приложении — только статус (см. §6) |
| Разработка на два клиента (веб+приложение) съедает время | React Native/Expo + переиспользование типов из монорепо вместо отдельного стека |
| Плохой интернет на конвентах, где приложение реально нужно | Офлайн-кэш «своих» данных, фоновая загрузка фото с индикатором, не блокирующая интерфейс |
| Push не доходит / игнорируется | Дублировать критичные уведомления (заявка, дедлайн, согласие) и push, и в центре уведомлений внутри приложения |
